# AMS deployment preparation

## Recommended layout

- **Vercel** serves the existing Vite/React frontend from the repository root with `frontend/` as its Root Directory and `dist` as the output directory.
- **Render** runs the FastAPI Docker web service and notification worker.
- **Render Postgres** is the managed PostgreSQL 16 database (with pgvector), connected over Render's private network. It is preferable to a self-managed database container for a public deployment because it provides managed persistence and backup options.
- Use an S3-compatible bucket for request documents. The Render service filesystem is ephemeral; local uploads are only suitable for development.

`vercel.json` provides the SPA route fallback. `render.yaml` is a Blueprint for API, worker, and database. It does not deploy anything until connected to the Git repository and applied in Render.

## Configuration order

1. Create the Render Blueprint from `render.yaml` in the Singapore region (or change all Render regions together before first creation).
2. Set `AMS_CORS_ORIGINS` on `ams-api` to a JSON array containing the exact deployed Vercel origin, for example `["https://ams-example.vercel.app"]`. Set `AMS_FRONTEND_BASE_URL` to that same origin. Do not include a trailing slash. The notification worker references these API settings so both services validate the same origin.
3. Set the S3-compatible bucket, region, endpoint (blank for AWS), and credentials on `ams-api`. The worker references these settings from the API service, so configure the provider values once. Keep the bucket private; uploaded documents are served only after API authorization.
4. Set SMTP credentials if password reset email is required. Twilio environment values are optional unless SMS is enabled in system settings.
5. Create the Vercel project with Root Directory `frontend`, Framework Preset `Vite`, and `VITE_API_BASE_URL=https://<ams-api-service>.onrender.com`. Set this for Production and Preview environments only when the API CORS allowlist includes each origin.
6. Configure a Vercel production domain, then update Render's CORS and frontend base URL with the exact domain. Deploy the frontend and verify login, logout, and a protected request from that origin.
7. Create the first production administrator by setting `AMS_BOOTSTRAP_ADMIN_EMAIL`, `AMS_BOOTSTRAP_ADMIN_ID`, `AMS_BOOTSTRAP_ADMIN_NAME`, and a strong `AMS_BOOTSTRAP_ADMIN_PASSWORD` for a one-time `python -m scripts.seed_admin` invocation in the API service shell. Remove the bootstrap variables after the account is created. **Do not use the development demo seeder in production.**

### Vercel project settings

Set Root Directory to `frontend`, Framework Preset to Vite, install command to `npm ci`, build command to `npm run build`, and output directory to `dist`. The `frontend/vercel.json` file contains the SPA route rewrite. Set `VITE_API_BASE_URL` to the Render API's HTTPS URL for each Vercel environment that should reach the API. Only allow a Preview deployment's exact origin in Render if it is intended to access real data. Rebuild after changing this value because Vite embeds it in the output.

## Exact environment values and ownership

The owner supplies the deployed Vercel origin and Render API URL. The Vercel project needs `VITE_API_BASE_URL=https://<ams-api-service>.onrender.com`; return that API URL to the Vercel owner. Return the Vercel origin (scheme and host only) to the Render owner for `AMS_FRONTEND_BASE_URL` and `AMS_CORS_ORIGINS` (a one-item JSON array, for example `["https://ams.example"]`). Include each separate preview origin only if it should be allowed to authenticate.

Render provides the private `AMS_DATABASE_URL` through its managed PostgreSQL connection and generates `AMS_SECRET_KEY`. The Blueprint sets `AMS_ENV=production`, `AMS_API_PREFIX=/api`, `AMS_COOKIE_SAMESITE=none`, and `AMS_STORAGE_BACKEND=s3`. Render must also be given the exact frontend values above and the provider values below:

`POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD` are local Compose initialization variables, not Render application settings. `AMS_STORAGE_PATH`, `AMS_DEMO_PASSWORD`, and `AMS_SEED_DEMO` are development-only. Do not copy demo values into cloud services. The Blueprint requests Render Postgres plan `basic-256mb` (legacy plan name; current plan ID `0.1c-256mb` is listed with a 100-connection maximum). Render also documents older legacy Postgres instance types at 97 connections for databases up to 6 GB RAM. The owner's actual database plan and legacy/new instance classification have not been inspected; verify them in Render before applying or scaling this Blueprint, and budget 97 until confirmed. Budget peak connections as `(API instances × (pool size + overflow)) + (worker instances × (pool size + overflow)) + migration/admin/monitoring connections`. One API plus one worker can use 30 pool connections total, leaving at most 67 connections for migrations, monitoring and administration under the conservative 97-connection budget. Keep operational headroom and re-evaluate when scaling API or workers. Confirm the selected plan against [Render's current compute plan table](https://render.com/docs/compute-plans) and [Postgres connection guidance](https://render.com/docs/postgresql-creating-connecting) before applying the Blueprint.

The vision adapter currently hard-codes the InsightFace `buffalo_l` model name. The Docker image does not install the optional vision extra. Enabling inference requires building with the repository's `[vision]` dependencies (`insightface`, `onnxruntime`, and `opencv-python-headless`) and provisioning the model files under InsightFace's expected model cache. Review the upstream model and pretrained-weight licensing before deployment. There is no model URL, model license, or model path environment variable in this repository today.

The production bootstrap variables are `AMS_BOOTSTRAP_ADMIN_EMAIL`, `AMS_BOOTSTRAP_ADMIN_ID`, `AMS_BOOTSTRAP_ADMIN_NAME`, and `AMS_BOOTSTRAP_ADMIN_PASSWORD`. The command now exits unless `AMS_ENV=production`, acquires a PostgreSQL transaction advisory lock, and refuses to create an account if any administrator already exists; the lock prevents two simultaneous bootstrap attempts. Set these values only for the one-time command, then remove them from the service environment. `AMS_SEED_DEMO` is not a production configuration option: the seeder exits unless `AMS_ENV=development`; never enable it on Render.

After the owner shares both URLs, run the production-origin smoke sequence: set Vercel `VITE_API_BASE_URL` and rebuild; set Render `AMS_FRONTEND_BASE_URL` and the exact `AMS_CORS_ORIGINS` array; then from the deployed Vercel origin log in, reload to verify `/api/auth/me` restores the session, call a role-authorized route, confirm an unsafe request with an unlisted `Origin` returns 403, log out, and verify session restoration no longer succeeds. Check cookie attributes `Secure`, `HttpOnly`, and `SameSite=None` in browser developer tools. This production test has not run because the URLs and cloud configuration are not yet supplied.

## Rollback and recovery

- **Migration startup:** Compose runs `alembic upgrade head` before the backend, and Render runs it in the API `dockerCommand` before starting Uvicorn. The worker does not run migrations. Every API instance started from this Blueprint would execute the migration command; there is no separate single-run migration service or cross-instance migration lock. Keep the API at one instance for staging migrations, and introduce a controlled one-off migration step before scaling API instances.

- **Vercel frontend:** use the Vercel project's Deployments page to promote the last known-good deployment. Confirm its environment still points to the intended Render API. If `VITE_API_BASE_URL` changed, promote or rebuild a deployment with the correct value.
- **Render API/worker code:** from each service's Deploys page, roll back to a recent successful deploy and check health/readiness and logs. A dashboard rollback disables automatic deploys for that service; re-enable them only after the faulty change is fixed. Check current environment variables after rollback because Render does not roll back all service configuration.
- **Database changes:** take and verify a database backup before a release that runs Alembic migrations. This API starts with `alembic upgrade head`; a code rollback does not reverse a schema migration. Keep migrations backward-compatible with the previously deployed API. If data recovery is needed, use Render Postgres point-in-time recovery to create a separate recovery instance, validate it, then update both API and worker `AMS_DATABASE_URL` settings to the verified instance. Retain the original database until the restored service is confirmed. Render's [rollback guide](https://render.com/docs/rollbacks) and [Postgres recovery guide](https://render.com/docs/postgresql-backups) describe recovery operations. Render currently documents PITR for paid Postgres; the recovery window is 3 days on Hobby and 7 days on Pro or higher workspace plans, while the Free compute plan has no PITR. Logical exports are retained for 7 days. Confirm the owner's workspace plan and database compute plan, required recovery window, and export availability in the dashboard; then rehearse restoration before launch.
- **Local logical backup:** use `pg_dump` before destructive development migrations and restore only to a disposable empty database with `pg_restore`; verify row counts and application readiness before using restored data.

The repository does not automate database backup scheduling or test cloud restores. The owner must enable/verify Render recovery on the selected plan and rehearse restoration before production data is entered.

## Cross-origin session requirements

The frontend and API use different hostnames, so production requires `AMS_COOKIE_SAMESITE=none`, HTTPS, `Secure` and `HttpOnly` cookies, and an exact CORS origin allowlist with credentials. The API also rejects unsafe browser requests whose `Origin` is outside that allowlist. Do not use a wildcard CORS origin with cookies.

The browser API base URL is compiled into the Vite bundle. Changing `VITE_API_BASE_URL` requires a new Vercel build/deployment.

## Local data fixtures

After starting the local Compose stack and applying migrations, run:

```powershell
docker compose exec -e AMS_SEED_DEMO=true backend python -m scripts.seed_demo
```

The idempotent, development-only seeder creates an admin, faculty, six students, one department/year/semester/section, three courses and allocations, timetable entries, conducted lecture attendance, a pending request, an announcement, a notification, and the attendance threshold. Set a private `AMS_DEMO_PASSWORD` of at least 12 characters in the ignored local `.env` before seeding; there is no committed default. The seeded users share that local password. The local Compose service bind-mounts this script read-only for development; the production Docker image deliberately does not include it. Never enable demo fixtures on a production database.

## Acceptance gates before public launch

- All Python unit and integration tests pass against PostgreSQL, plus frontend type-check/build.
- Login works with `SameSite=None` cookies from the real Vercel hostname; role-scoped student, faculty, and admin journeys pass.
- WebSocket attendance events work through the public Render endpoint.
- S3 uploads/download authorization and password reset email are verified with real provider credentials.
- Camera recognition is validated only with enrolled, consenting profiles and deployed vision dependencies; manual marking remains the fallback.
- Configure Render backup/recovery and monitor service health/logs. A 256 MB database is suitable only for a small project/demo workload; size it for expected data and connections.
- Current local verification: the backend test suite, 24 API smoke checks, frontend lint/build, dependency audits, and five consecutive 100-session probes passed in the local Compose environment. The probe results and the keep-alive root cause are recorded in `integration/README.md`. This uses eight seeded principals and a local database; it is not evidence for 100 distinct production users or production capacity compliance.

## Important limitations

- To update backend dependencies, change `backend/pyproject.toml`, then regenerate both backend lockfiles under Python 3.12 using pinned `pip-tools==7.5.2`: `python -m pip install pip-tools==7.5.2`, then `pip-compile --index-url https://pypi.org/simple --generate-hashes --resolver=backtracking --strip-extras --output-file=requirements.lock pyproject.toml` and `pip-compile --index-url https://pypi.org/simple --generate-hashes --resolver=backtracking --strip-extras --extra=dev --output-file=requirements-dev.lock pyproject.toml` from `backend/`. The production Dockerfile installs only `requirements.lock`; `requirements-dev.lock` is for test/lint tooling. Review resolved versions, run audits/tests, and build with `--no-cache`. To refresh the base, inspect the official `python:3.12-slim` manifest list with `docker buildx imagetools inspect python:3.12-slim`, update only the digest in `backend/Dockerfile`, then build and verify all supported deployment architectures. Keep the digest pinned between reviewed updates.

- This repository's UI is Vite/React rather than the design document's locked Next.js stack. Vercel supports the current Vite app, but the implementation remains a documented architecture deviation.
- The frontend uses `frontend/package-lock.json` and the documented Vercel install command is `npm ci`. The backend image installs only the hash-checked runtime dependencies in `backend/requirements.lock`; tests, Ruff and HTTPX are not installed in the production image. The Dockerfile pins the official Python 3.12 slim multi-platform image by manifest-list digest. These pins make dependency and base-image selection reproducible; they do not make the entire build byte-for-byte reproducible because package build environments, OS package layers and Docker/BuildKit versions also affect output.
- The Render Blueprint configures an S3-compatible storage backend and requests its settings; external bucket creation and credentials are account-side steps.
- Only `render.yaml` was reviewed here; the owner's actual Render database/service plan and workspace recovery entitlement were not accessible. Verify them in the dashboard before relying on the 100-connection budget or PITR/backups.
- Real provider credentials, custom domains, deployment, and first production admin provisioning must be supplied/applied in the relevant cloud accounts.
- The resets from an earlier 100-session run were traced to Uvicorn's 5-second default keep-alive timeout interacting with the synchronized read barrier and per-session HTTP connection reuse. The API now uses a 30-second keep-alive timeout; five consecutive local probes against the rebuilt image passed 100/100 reads and logouts with no resets or HTTP/pool errors. The API semaphore remains 15 and the pool remains 5 + 10. This result is limited to the local seeded workload and eight unique principals. The prior unbounded burst exposed pool saturation and led to the request bound and generic retryable 503 handling. See `integration/README.md` for per-run measurements.
- Local security regressions cover password reset/session revocation, production cookie flags, document signatures/authorization, provider outage mapping, sanitized worker errors, and safe security headers. Account lockout exists, but there is no IP-based API rate limiter; configure edge/WAF rate limiting before public exposure. npm audit reports zero known vulnerabilities and pip-audit reports none for installed PyPI packages. Real S3/email/SMS behavior, production-origin cookies, vision inference, and biometric retention/deletion policy remain owner/deployment gates.
